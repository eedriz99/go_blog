## Running the Project

### Prerequisites
- Go 1.21+
- PostgreSQL running locally

### Steps

```bash
# 1. Clone
git clone https://github.com/eedriz99/go_blog.git
cd go_blog

# 2. Set env vars (or export individually — see Environment Variables section)
export DB_ADDR="postgres://admin:adminpassword@localhost/go_blog?sslmode=disable"

# 3. Run migrations
./migrate.sh up

# 4. (Optional) Seed the DB
go run ./cmd/seed/

# 5. Start the server
go run ./cmd/api/
# or with hot reload:
air
```

Server runs at `http://localhost:8000`.
Swagger UI: `http://localhost:8000/swagger/index.html`

## Architecture & Data Flow

```
HTTP Request
    │
    ▼
Chi Router (api.go)
    │
    ├── Middleware (postContextMiddleware / userContextMiddleware)
    │       └── Fetches resource from DB → injects into request context
    │
    ▼
Handler (cmd/api/*.go)
    │
    ├── readJSON()         → parse + validate request body
    ├── store.XXX.Method() → DB operation via store layer
    └── writeJSON()        → encode + send JSON response
            │
            ▼
        Store (internal/store/*.go)
                │
                └── database/sql queries against PostgreSQL
```

**Key principle:** handlers orchestrate, stores query, models represent DB shape. Nothing crosses those boundaries.

## Store (Database Layer)

Defined in `internal/store/`. Each resource has its own store file implementing the interface declared in `storage.go`.

### `Storage` struct (`storage.go`)

```go
type Storage struct {
    Posts    interface { Create / GetByID / GetByUserID / GetAll / Update / Delete }
    Users    interface { Create / GetByID / Update / Delete }
    Comments interface { Create / GetByPostID / Update / Delete / GetByUser }
}
```

`NewStore(db)` constructs the Storage and wires the concrete implementations.

### Store files

| File | Struct | Methods |
|------|--------|---------|
| `user.go` | `UserStore` | `Create`, `GetByID`, `Update`, `Delete` |
| `post.go` | `PostStore` | `Create`, `GetByID`, `GetByUserID`, `GetAll`, `Update`, `Delete` |
| `comment.go` | `CommentStore` | `Create`, `GetByPostID`, `Update`, `Delete`, `GetByUser` |

### Shared types (`mediator.go`)

`CommentWithUsername` — a join result used by `GetByPostID` to include the author's username without a second query.

### Sentinel errors (`storage.go`)

```go
store.ErrorNotFound   // → 404
store.ErrorInternal   // → 500
store.ErrorBadRequest // → 400
```

Always check against these with `errors.Is()` in handlers.

## DTOs — Payloads & Responses

The DTO layer keeps handler logic clean and prevents model internals (e.g. `Password`) leaking into responses.

### Payloads (`internal/dto/payload/`) — what comes IN

| Type | Fields |
|------|--------|
| `payload.CreatePostPayload` | `title`, `content`, `tags` |
| `payload.UpdatePostPayload` | `title*`, `content*`, `tags*` (all optional pointers) |
| `payload.CreateCommentPayload` | `content`, `post_id` |
| `payload.UpdateCommentPayload` | `id`, `user_id`, `content` |
| `payload.DeleteCommentPayload` | `id`, `user_id` |

### Responses (`internal/dto/response/`) — what goes OUT

| Type | Description |
|------|-------------|
| `response.PostResponse` | Single post |
| `response.PostListResponse` | `{ data: [], total: n }` |
| `response.PostWithCommentsResponse` | Post + embedded comment list |
| `response.CommentResponse` | Single comment (with optional `username`) |
| `response.CommentListResponse` | `{ data: [], total: n }` |
| `response.UserResponse` | Public user fields (no password) |

Constructor functions (`NewPostResponse`, `NewCommentResponse`, etc.) are the only way to create response objects — don't construct them manually in handlers.

## Middleware

Defined in `cmd/api/middleware.go`.

### `postContextMiddleware`
Applied to all `/v1/posts/{postID}` sub-routes. Fetches the post from the DB using `{postID}` and injects it into the request context. Handlers retrieve it via `getpostFromContext(r)`.

### `userContextMiddleware`
Applied to all `/v1/users/{userID}` sub-routes. Fetches the user from the DB using `{userID}` and injects it into the request context. Handlers retrieve it via `getUserFromContext(r)`.

> **Important:** Both middlewares are registered at the route group level where the URL param is defined (e.g. `r.Route("/posts/{postID}", ...)`). Never apply them at a parent group — chi won't have resolved the param yet and the query will receive an empty string.

## Utility Packages

### `cmd/api/json.go`
| Function | Purpose |
|----------|---------|
| `readJSON(w, r, &dst)` | Decodes JSON body into `dst`; enforces 1MB limit and rejects unknown fields |
| `writeJSON(w, status, data)` | Encodes `data` as JSON with correct Content-Type header |
| `writeError(w, status, msg)` | Wraps `msg` in `{ "error": "..." }` envelope and calls `writeJSON` |

### `cmd/api/errors.go`
| Function | HTTP Status |
|----------|-------------|
| `app.InternalServerError(w, r, err)` | 500 |
| `app.BadRequestError(w, r, err)` | 400 |
| `app.ResourceNotFoundError(w, r, err)` | 404 |

### `internal/env/env.go`
Typed env var helpers with fallback defaults — `GetString`, `GetInt`, `GetDuration`. All config is read at startup in `main.go`.

### `internal/db/postgresdb.go`
`db.New(addr, maxIdle, maxOpen, maxIdleTime)` — opens the connection, configures the pool, and pings with a 5s timeout.

## Database Migrations

Migrations live in `db/migrations/` as paired `.up.sql` / `.down.sql` files, named by timestamp.

| Timestamp | Description |
|-----------|-------------|
| `20260129180904` | Init |
| `20260129181640` | Create users table |
| `20260129191442` | Create posts table |
| `20260209211936` | Create comments table |
| `20260416231924` | Alter comments |
| `20260625095116` | Add password column to users |

```bash
./migrate.sh up        # apply all pending migrations
./migrate.sh down      # roll back last migration
./migrate.sh status    # show migration state
./migrate.sh create <name>  # create a new migration pair
```

## Seeder

`internal/db/seeder.go` + `cmd/seed/main.go`

Inserts synthetic data in dependency order:
1. **100 users** — names drawn from a diverse 100-name pool; password `"password123"`
2. **~160 posts** — one per entry in the `posts` data slice; each assigned to a random user
3. **~480 comments** — 3× the post count; random user commenting on a random post

Run:
```bash
go run ./cmd/seed/
```

> Re-running the seeder appends data — it does not wipe existing rows first.

## Conventions

- **No cross-layer leakage** — models stay in `model/`, responses stay in `response/`. Never return a `model.User` directly from a handler.
- **Context carries resources** — middleware fetches DB records and puts them in `r.Context()`. Handlers read them via `getpostFromContext` / `getUserFromContext`. Do not re-fetch in the handler.
- **Errors are sentinel values** — return `store.ErrorNotFound` etc. from the store; handle with `errors.Is()` in handlers to map to the right HTTP status.
- **UserID comes from context** — currently a placeholder UUID. When auth is added, it will come from the JWT middleware, never from the request body.
- **Swagger annotations are required** — every new handler needs `@Summary`, `@Tags`, `@Router`, and appropriate `@Param`/`@Success`/`@Failure` lines. Run `swag init` after adding them.
- **Push to `claude` branch** — all changes go to the `claude` branch via `git push origin main:claude`.
